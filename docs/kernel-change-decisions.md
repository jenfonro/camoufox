## 通用接口原则

用户新增要求（2026-09-11）：这是内核修改，参数与画像数据应面向通用
管理器，不为 Nimbo 的档案结构或业务逻辑专门设计。需要参考 VirtualBrowser、
polyackiy/camoufox-profile-manager 及 Firefox 管理器生态。

本轮已调研 VirtualBrowser、CPM、Kameleo/Junglefox、Multilogin/Stealthfox
公开接口，并对照 W3C WebGPU、Firefox 152 WebIDL 和 Firefox WebDriver
配置约定。建议画像内部字段采用标准名称、类型及对象关系，外层延续
Camoufox 配置习惯，各管理器负责自己的格式转换。

用户再次确认：Firefox 自身的通用机制优先，其他产品只参考，不复制
它们的专有模式或协议。已有的开关优先复用原生机制，缺少的画像覆盖
才扩展配置；保留原生对象、上下文条件以及设备请求与执行语义。
用户提供的所有参考项目和 PR 都遵循这一边界，不因阅读参考资料
自动增加生成器、管理器或整套算法的移植范围。

助手已依据本次授权确定通用接口：`gfx:hardwareAcceleration`、
`webgpu:enabled`、`webgpu:profile`，通过现有 `CAMOU_CONFIG` 承载。
研究依据见[WebGPU 画像接口通用性调研](webgpu-interface-research.md)；
其中的历史候选规则已由配置规范 v1 收敛，不再作为未决事项。

## 事项 1：硬件加速与 WebGPU 暴露独立控制

状态：已实现，Windows x64 运行验收通过。

目标：尽量保留 Camoufox 上游默认行为，由内核提供一个可选的布尔配置，
让管理器按需解除 Camoufox 自带的硬件加速禁用策略。思路与已完成的窗口
配置扩展一致：保留原调用方式，通过额外参数开放能力。

用户随后明确调整：硬件加速打开或关闭，都不应自动向网页开放 WebGPU。
增加独立参数控制 WebGPU 是否暴露，默认不暴露；开启暴露后的画像控制
属于事项 2。此前“打开硬件加速即可直接暴露原生 WebGPU 报告”的理解
不再作为目标。

### 硬件加速开关：`gfx:hardwareAcceleration`

| 启动参数 | 内核行为 |
| --- | --- |
| 不传 | 保留上游原有禁用策略 |
| `false` | 保留上游原有禁用策略 |
| `true` | 解除 Camoufox 自带的这条禁用策略，沿用 Firefox 原有图形初始化与兼容性判断；不隐含开放网页 WebGPU |

参数在启动时、图形初始化之前读取并生效，改变参数需要重启进程。
每次启动按本次参数决定行为，不因前一次启用而改变后一次不传参数的语义。
新构建已支持该配置键。开启只解除 Camoufox 自带禁用
策略，其他原生图形偏好和兼容性条件继续按 Firefox 规则处理。

### WebGPU 暴露开关：`webgpu:enabled`

| 暴露参数 | 画像输入 | 预期行为 |
| --- | --- | --- |
| 不传或 `false` | 任意 | 不向网页提供可用 WebGPU，BrowserScan 的 WebGPU Report 显示 `not support`，与硬件加速开关的状态无关 |
| `true` | 没有任何画像数据 | 沿用当前内核在所选后端上的原生返回值 |
| `true` | 提供档案画像 | 按事项 2 的画像配置呈现 WebGPU 数据 |

硬件加速开启、WebGPU 暴露关闭时，浏览器内部仍可使用可用 GPU 进行
正常图形处理。这里控制的是 WebGPU 接口，不代表同时关闭或隐藏 WebGL、
Canvas 等其他接口。

需要区分当前事实与预期行为：上游实测是接口存在、适配器获取失败；
采用 Firefox 原生开关关闭 WebGPU 则会改变接口是否暴露。虽然两者
都可显示 `not support`，“默认不暴露”仍是本方案明确新增的行为，不能
称为网页 API 层面完全保持上游原样。

用户已明确：选择暴露却未提供画像时，直接保留原生行为。内核不替管理器
生成或补齐画像，不因缺少画像而关闭接口或增加报错。是否暴露、是否需要
画像、传入什么画像，均由管理器负责适配。

原生返回值包括当前内核已有的信息处理、空字段、能力限制和正常失败
返回，并非额外补齐全部物理硬件信息。暴露开关只是接口开放条件，不能
凭空创建适配器；没有可用适配器时仍按原生行为处理。

### 内核与管理器的职责

- 内核分别开放硬件加速和 WebGPU 暴露配置，不用
  `layers.acceleration.force-enabled=true` 或其他强制开启手段代替硬件开关。
- 开启时解除的是 Camoufox 自带的禁用策略，不跳过 Firefox 原有的设备
  能力与兼容性判断。
- 是否传参、何时开启、如何选择硬件或软件后端，由管理器适配。
- 本事项不新增自动模式、硬件优先、自动回退或 WARP 选择逻辑；Firefox
  本身已有的初始化行为继续沿用。
- GPU 画像、WebGPU 身份字段、功能列表和限制值的控制归事项 2。
  三个配置入口的名称、数据形状及读取规则已经写入配置规范 v1。

### 已知依据

当前 `settings/distribution/policies.json` 的
`"HardwareAcceleration": false` 会在启动时设置并锁定
`layers.acceleration.disabled=true`。它导致本次 Windows 构建走软件合成，
随后 WebGPU 适配器匹配失败。

此前在独立测试副本中移除这条策略，已经验证无需强制开启即可正常取得
WebGPU 适配器；旧型号画像也不导致不支持。另一次 WARP 测试验证了 CPU
适配器路径，但没有完成无 GPU 服务器部署验收。

这些实验只证明可行性，不表示正式内核默认值已改变，也不表示本事项
应全局删除原来的禁用策略。完整证据见
[WebGPU 启动调查](webgpu-startup-findings.md)。

## 事项 2：WebGPU 档案画像与报告数据控制

状态：接口与能力控制已实现，Windows x64 运行验收通过。

用户指出：直接开放当前原生 WebGPU，同机多档案会返回相同的本机报告
和哈希。第二项要解决的是开放接口后的数据来源与画像一致性。

- 需要画像时，由管理器生成、保存并传入，内核按配置呈现 WebGPU 数据。
- 暴露开启但没有任何画像输入时，返回当前内核原生数据；这属于明确
  支持的用法，不作为需要内核兜底的配置错误。
- 同一档案的画像数据跨启动保持稳定，不再依赖每次启动随机生成。
- 不同档案可传入不同画像；没有传画像的档案继续得到原生报告，即使
  同机多个档案因此具有相同报告，也由管理器的配置选择决定。
- 网站自行根据报告数据计算哈希；内核需要控制产生哈希的输入，不能
  将需求理解为直接指定 BrowserScan 的某个哈希字符串。
- 硬件或软件后端负责实际执行，画像控制对外数据；声明的功能和限制值
  应能被选用后端兑现，不能只改变报告而使实际调用失败。

`webgpu:profile` 包含 `gpu`、通用 `adapter` 和 `adapterOverrides`。
已确定的规则：

- `info`、`limits` 逐字段覆盖；features 和 WGSL 功能集合显式传入时
  整体替换，未传仍继承原生或前一层值。
- 按标准适配器请求选项匹配覆盖；条件更多者优先，歧义条件报错，
  配置数组顺序不改变结果。
- 覆盖当前 Firefox 的标准身份、功能、限制值、WGSL 功能及首选
  画布格式；派生设备及原生支持的 Worker 采用一致语义。
- 未传画像是原生模式；无效类型、越界或歧义为配置错误。画像能力
  与实际后端不兼容时，该次适配器请求正常失败并记录原因，不更换
  画像、不自动造功能，也不关闭整个 WebGPU 接口。

已有离线对比确认，CPU/GPU 报告的可见差异主要在适配器条目数量和
回退标记；因此单独修改型号不是完整画像能力。通用配置只保证受控
数据的确定性，不承诺任意后端的像素、性能或所有站点哈希都相同。
完整字段、数值范围、优先级、例子和后续验证要求见配置规范 v1。

## 通用本地控制接口：已实现并验收

2026-09-23：用户要求正常启动的 Camoufox 能被外部程序完整控制，
无需启用 BiDi、Marionette、Juggler 调试会话或依赖普通扩展。
新入口不向网页新增控制标记；实际不初始化相关调试链，
不能仅修改检测字段或更换传输形式。

本阶段只做 Camoufox 内核。auto-manager 是能力需求的参考，
其 Agent、扩展/BiDi 移除和 VNC 收敛由管理器另行适配；
不考虑 Chrome，不引入管理器或站点业务字段。
接口以 Firefox 原生机制和标准浏览器对象为基础，采用通用、清晰的
参数、版本、能力与错误语义。启动字段已确定为 `control:enabled`、
`control:port`、`control:token`、`control:endpoint`；默认关闭。

复用基线为已推送的 `codex/sync-upstream-20260923` / `e46a454`，
包含此前窗口、WebGPU、持久化和表单/密码策略改动。
详细源码依据、范围、未决项、实施步骤和严格验收标准已记录在工作清单，
构建目录、代理与环境差异见构建环境文档。
